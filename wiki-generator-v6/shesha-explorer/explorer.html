SheshaExplorer — How it works

What you're looking at

SheshaExplorer maps your Shesha .NET project into a relationship graph by reflecting your compiled assemblies. Every AppService method, Domain Entity, Repository, API Endpoint, and Permission becomes a node. The connections between them — who calls what, what is authorised by which permission, which service operates on which entity — become edges.

Load a graph.json file produced by running SheshaExplorer against your project's compiled DLLs. Once loaded, every node is clickable. The right panel shows its details, relationships, and lets you run the cellular automaton from it.

Use / to search · ↑↓ to navigate · Enter to propagate CA · Esc to clear

The five node types

ColourTypeWhat it represents
AppService method Business logic — a method on a class inheriting ApplicationService
Domain Entity A database-mapped class inheriting Entity or FullAuditedEntity
Repository An IRepository interface or implementation
API Endpoint A controller action with an HTTP verb attribute
Permission A [ShaAuthorize] permission definition
Hotspot Any node with a coupling score ≥ 3.0 — change carefully
Dead candidate A node never reached from any entry point — possible dead code

Use the filter chips in the left panel to show or hide any node type.

The cellular automaton

Click any node then press "Propagate from this node" in the right panel (or press Enter). The CA seeds from that node at generation 0.

In generation 1 every directly connected node activates. In generation 2 every node connected to those activates. This continues until nothing new fires.

The result is the complete blast radius — everything that could be affected if the selected node changes. Activated nodes stay bright. Unaffected nodes grey out.

Nodes that are never activated from any entry point across all runs are dead code candidates — nothing in the system reaches them through any path.

Press Escape to clear the propagation and restore the full graph view.

Coupling scores

The coupling score is computed by running the CA from every AppService method and API endpoint in the project, and recording at which generation each node was activated. The mean activation generation is the score.

Score 1.0 — only ever reached directly from one or two places. Safe to change in isolation.

Score 3.0+ — reached after many hops from many different starting points. Many things depend on it indirectly. Shown with an orange ring in the graph.

Score 4.0+ — highly coupled. A change here has a wide blast radius. Deserves extra test coverage and careful code review before modifying.

The coupling score does not mean the code is buggy — it means it is load-bearing. The most important nodes in a well-designed system will naturally have high scores.
